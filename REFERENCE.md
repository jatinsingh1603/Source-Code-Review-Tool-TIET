## 1. How to read this file

- **One section per family.** Sections 2 to 11 each cover one family of frameworks. Every table has the same columns: *Framework*, *Version/Year*, *Publisher*, *Link*, *How CodeKavach uses it*.
- **Each entry appears once in this file.** An entry is listed under the family where it does most of its work; other sections point to it with a "see also" note. About sixty entries also have a row in RESOURCE.md, by design: interchange formats and data feeds (section 9, and EPSS, KEV and Vulnrichment in section 7.1), the supporting studies of sections 7.2 and 10.4, the public audit reports of section 10.3 and the AI threat taxonomies of section 11. This file is authoritative for version, publisher and how the framework is used; RESOURCE.md is authoritative for licence, role tag and integration notes. When one of these entries changes, update both rows in the same commit. Section 12 shows how the entries combine on a single finding, and section 13 shows which pipeline stage and which report element each one informs. Section 14 collects licensing and status caveats.
- **Bold names are core.** A framework in bold is rated core in the project's research notes or is named in `docs/ARCHITECTURE.md`, section 8: the default pipeline, the default report template or the evaluation depends on it. The remaining entries are mapping targets, optional annexes, design inspiration or related-work citations.
- **Links were verified on 2026-09-21.** Every entry comes from the project's research files, where each URL was requested and each title, version and publisher was checked against the live page, the publisher's repository or a bibliographic service. Only entries that passed that check are listed. Where two links are given, the first is the canonical page and the second is the specification text, repository, DOI or companion page recorded for the same entry. A few publishers (iso.org, misra.org.uk, gao.gov, ithandbook.ffiec.gov) refuse automated requests; those URLs and titles were confirmed through independent search results.
- **Version/Year is the edition CodeKavach targets.** "Living" means the publisher updates the page or service without version numbers; "Undated" means the research files record no publication year. Cite living pages with an access date.
- **"Uses" describes design intent.** The last column states how the framework is used in the design in `docs/ARCHITECTURE.md` and `docs/PLAN.md`. It is a plan of record, not a claim that the feature already exists; follow the issue tracker for implementation status.
- **Supporting studies.** Sections 7.2 and 10.4 list the empirical studies that justify specific methodology choices. The wider research literature is in RESOURCE.md.

## 2. OWASP

OWASP material supplies the manual review process that CodeKavach automates, the control catalogue used in the compliance annex, and the awareness lists that clients and regulators quote in statements of work. OWASP content is mostly CC BY-SA: CodeKavach links to it and paraphrases it, and keeps any bundled text in a separately licensed data directory. See also: OWASP Risk Rating Methodology (section 7.1), SAMM and the Threat Modeling Cheat Sheet (section 6), CycloneDX and OPTRS (section 9), the WSTG reporting chapter (section 10.1) and the OWASP LLM and agentic lists (section 11).

## 3. MITRE and weakness taxonomies

CWE is the primary key of every CodeKavach finding and the join key to almost every other framework in this file. CWE identifiers carry no client information, so they may be sent to the LLM at every privacy level. See also: CWSS (section 7.1) and MITRE ATLAS (section 11).

### 12.4 How the identifiers travel

- **SARIF 2.1.0.** CWE and OWASP references go in `taxonomies`; the CVSS vector, confidence, privacy level used and model identity go in `result.properties`; `partialFingerprints` give the stable identity used for de-duplication and issue sync; `properties.security-severity` is set from the CVSS score for GitHub code scanning; LLM-dismissed false positives are recorded as `suppressions` with a justification.
- **PDF, DOCX and HTML reports.** Each detailed finding prints its identifiers in a header block, and the rating-definition appendix defines every severity label and scoring system used in the same document.
- **CSV and XLSX.** The column set follows the finding table that SEBI's CSCRF and CERT-In's audit guidelines prescribe, so rows can be pasted into a regulator-facing report.
- **GitHub issues and Projects.** Issues carry severity and CWE labels and a fingerprint marker; the SSVC decision selects the Kanban lane.

An illustrative shape, using the field names of the `Finding` model (the normative schema is exported to `docs/schemas/`):

```json
{
  "id": "<PREFIX>-001",
  "cwe": "CWE-89",
  "owasp": ["A05 Injection (Top 10:2025)"],
  "asvs": "<ASVS 5.0.0 requirement identifier>",
  "capec": "<CAPEC identifier, where known>",
  "cvss4_vector": "<CVSS:4.0 vector string>",
  "cvss4_nomenclature": "CVSS-BE",
  "cvss31_vector": "<CVSS:3.1 vector string>",
  "likelihood": "<1 to 5>",
  "impact": "<1 to 5>",
  "compliance": [
    {"framework": "PCI DSS v4.0.1", "clause": "6.2.4"},
    {"framework": "ISO/IEC 27001:2022", "clause": "A 8.28"}
  ],
  "confidence": "<0 to 1>",
  "provenance": {"engine": "<engine and rule id>", "llm": "<provider, model, privacy level>"}
}
```

### 12.5 What is sent to the LLM and what stays local

CWE identifiers and public taxonomy labels carry no client information and may appear in prompts at every privacy level. Everything that expresses the client's context stays local: the asset profile, CVSS Environmental metrics, OWASP business-impact factors, SSVC mission impact, compliance scope and the clause mapping itself. The LLM may propose a CWE, a CVSS Base vector and an impact narrative in pseudonym space; each proposal is validated against local deterministic evidence before it is recorded, and findings from deterministic engines are not discarded because a model disagrees.

## 13. Review methodology lineage

CodeKavach automates a manual process that has a long published history: Fagan's inspections (1976), the review and audit types of IEEE Std 1028, code review as the first software-security touchpoint (McGraw, 2004), the OWASP Code Review Guide (2017) and its Secure Code Review Cheat Sheet, and the reporting conventions of professional audit firms. The privacy layer and the LLM stage are the new elements; the rest of the workflow follows these sources deliberately so that auditors recognise it.

## 14. Licensing, status and citation caveats

- **Paid or proprietary texts.** ISO/IEC, IEC, IEEE and MISRA documents are cited by number and title; their text is not reproduced, and MISRA rule headlines are not shipped. CIS Controls are CC BY-NC-ND 4.0 and CIS Benchmarks are CC BY-NC-SA 4.0 ([CIS terms of use](https://www.cisecurity.org/terms-of-use-for-non-member-cis-products)), and OSSTMM is NonCommercial-NoDerivs, so all three are referenced by identifier and link only. COBIT 2019 is proprietary ISACA text and is cited by objective identifier. SSVC prose documentation is CC BY-NC 4.0 while its data and software files are under an MIT-style licence.
- **Share-alike content.** OWASP documents are mostly CC BY-SA 4.0. CodeKavach links to them and paraphrases; if text is bundled it sits in a separately licensed data directory, outside the MIT-licensed code.
- **External datasets.** OWASP Benchmark is GPL-2.0 and is pulled at evaluation time, not vendored. NIST Bugs Framework data is not embedded because of its stated patent and licensing position.
- **Status notes to repeat when citing.** OWASP Top 10:2025 is mapped through a CWE view still titled "RC1 (2025)". EDPB Guidelines 01/2025 is the public-consultation version. NIST SSDF v1.2 is an initial public draft, and the US federal self-attestation mandate that referenced SSDF was rescinded in January 2026. OWASP OPTRS and AISVS are early-stage. NIST LEV is a proposed metric. IEEE Std 1028-2008 is in inactive-reserved status. The Google eng-practices and CNCF tag-security repositories are archived, so a commit is pinned when citing them. The RBI 2016 circular says banks "may consider" source code audits, and the 2019 UCB framework says UCBs "may conduct" them, which is weaker wording than the later Master Directions. Article 29 WP Opinion 05/2014 predates the GDPR and is cited for its three-risk test, which the EDPB continues to use; it is not current binding guidance.
- **Clause numbers.** RBI paragraph numbers for the 2021 and 2023 Master Directions and the SEBI CSCRF provisions were confirmed against the published texts. GAO Yellow Book paragraph numbers and ISO 19011 clause 6.5 were confirmed from secondary sources only and are quoted after the primary text has been read.
- **Moved URLs.** After OWASP's site migration the legacy `owasp.org/www-project-*` paths for several projects return 404; use the URLs in this file. The SEI CERT wiki has moved to `cmu-sei.github.io`. The old `samate.nist.gov/BF/` address and the `first.org/epss/model` and `/epss/api` paths return 404. The PTES site is served over `http://` only.
- **Not legal advice.** Regulatory entries describe how CodeKavach output can be used as evidence. They are an engineering mapping, not a legal opinion, and CodeKavach reports do not state that a client complies with a regulation. Identifier pseudonymisation of source code is an analogy to pseudonymisation under data-protection law, not an instance of it, unless the identifiers relate to natural persons.

## 15. Maintaining this file

1. Add a framework only after its URL returns HTTP 200 (or is confirmed through the publisher's catalogue when the site blocks automated requests) and the page says what it is cited for. Record the check in the research notes under `docs/research/`.
2. Keep one row per framework. If a framework matters to a second family, add a "see also" note instead of a second row.
3. When a framework publishes a new version, update the row, the mapping table in `data/` and the affected report templates in the same change, and note the change in `CHANGELOG.md`.
4. Research papers, datasets, tools and libraries belong in [RESOURCE.md](RESOURCE.md). A study is listed here only when it directly justifies a rule of the review methodology (sections 7.2 and 10.4).
