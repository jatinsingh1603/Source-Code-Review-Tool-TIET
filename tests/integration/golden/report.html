This report presents the secure source code review of KavachBank. The review was performed on with CodeKavach, combining deterministic rule and taint analysis with model-assisted triage under a privacy-preserving egress policy. 29 files and 936 lines of YAML, Python, JavaScript, Dockerfile, Terraform code were analysed.

The review identified 59 findings (15 critical, 25 high, 14 medium, 5 low). The overall security posture is rated critical: at least one weakness can be exploited to compromise the application or its data, and immediate action is required. 6 findings are supported by a complete source-to-sink data-flow trace.

Severity distribution

Most significant findings

  • CK-2026-001 (Critical): A pull_request_target workflow checks out the pull request head, running untrusted code with repository secrets and a write token. An attacker can run code with the pipeline's secrets and write token, tamper with releases and pivot into the supply chain.
  • CK-2026-002 (Critical): Container 'api' is privileged. Any other weakness in the component becomes a full host or cluster compromise, because the attacker inherits the excess privileges.
  • CK-2026-003 (Critical): Data from a http_param source reaches a sql sink (cur.execute). An attacker can read, modify or delete database records outside their authorisation, bypass authentication and, on some engines, execute commands on the database host.
  • CK-2026-004 (Critical): Hard-coded credential of type connection_string (masked preview po****** (51 chars), entropy 4.91 bits/char). Anyone with access to the repository, a build artefact or a decompiled binary obtains the credential; rotating it requires a code change and redeployment.
  • CK-2026-005 (Critical): Hard-coded credential of type aws_access_key (masked preview AK****** (20 chars), entropy 3.68 bits/char). Anyone with access to the repository, a build artefact or a decompiled binary obtains the credential; rotating it requires a code change and redeployment.

Where the weaknesses concentrate

The most frequent weakness classes are CWE-798 Use of Hard-coded Credentials (11); CWE-250 Execution with Unnecessary Privileges (8); CWE-1395 Dependency on Vulnerable Third-Party Component (8). By OWASP Top 10 category the largest group is A07:2021 Identification and Authentication Failures (12 findings). Recurring classes indicate a missing shared control rather than isolated mistakes, so the recommendations below address the control as well as each instance.

Strategic recommendations

  • Immediate (within 7 days): Revoke and rotate the exposed credential immediately, then load it at run time from a secret manager or environment. [CK-2026-004, CK-2026-005, CK-2026-006, CK-2026-007 and others]
  • Immediate (within 7 days): Upgrade the component to a fixed version, or remove it if it is not needed. [CK-2026-015]
  • Short term (within 30 days): Upgrade the component to a fixed version, or remove it if it is not needed. [CK-2026-026, CK-2026-027, CK-2026-037, CK-2026-038 and others]
  • Short term (within 30 days): Run the component as a non-root user, drop the privileged flag and grant only the capabilities it needs. [CK-2026-018, CK-2026-019, CK-2026-021, CK-2026-022]
  • Medium term (within 90 days): Run the component as a non-root user, drop the privileged flag and grant only the capabilities it needs. [CK-2026-041, CK-2026-042, CK-2026-045]
  • Medium term (within 90 days): Encode output for its HTML context (or use a template engine with auto-escaping) and never send raw request data with res.send or equivalent. [CK-2026-049, CK-2026-052]
  • Planned (next release cycle): Do not check out untrusted code in privileged workflows; pin third-party actions to a full commit SHA and reduce the token permissions. [CK-2026-058, CK-2026-059]
  • Planned (next release cycle): Pin the component to a reviewed version or digest and replace unmaintained components. [CK-2026-055, CK-2026-057]
  • Embed the deterministic rules in CI so that the weakness classes found here are blocked at pull-request time, and schedule a retest once the fixes are deployed.

3Methodology

The review followed the phases of NIST SP 800-115 and the OWASP Code Review Guide, executed by the CodeKavach pipeline. Deterministic analysis finds candidates; a language model, reached only through a privacy-preserving egress guard, assesses them; every finding is then rated and mapped to recognised taxonomies.

PhaseStepDescription
PlanningScoping and policyScope, exclusions and the per-path privacy policy were fixed in the project configuration before the run; the configuration digest is recorded.
DiscoveryCode crawlFiles were discovered, their languages detected and parsed with Tree-sitter into syntax trees, symbols and call graphs.
AnalysisDeterministic analysisStructural security rules, intra- and inter-procedural taint analysis from sources to sinks, and the configured external engines produced candidates; duplicates were merged by fingerprint.
PrivacyPrivacy preparationEach candidate was cut to a minimal code slice, secrets and personal data were redacted and identifiers pseudonymised as the privacy level requires, and the payload re-scanned by an independent egress guard before any model call.
ValidationModel-assisted triageSanitised payloads were reviewed by the configured language model with structured output; every request is recorded in a hash-chained egress ledger. The model's answer is advisory: it can lower confidence but never closes a finding.
RatingRisk ratingFindings were rated by severity, CVSS where available, and on a five by five likelihood and impact matrix, then mapped to CWE, OWASP and compliance clauses.
ReportingReportingPseudonyms were restored locally, evidence was cut from the original files with secrets masked, and every report format was rendered from one document model with an integrity manifest.

Privacy levels

What leaves the client environment is governed by the privacy level. This review ran at L3.

CVSS v4.0 base scores are reported as CVSS-B (base metrics only); CVSS v3.1 vectors are given alongside for tools that do not yet read v4.0. Where a finding has no vector it is marked 'not scored' and its severity comes from the rule.

Likelihood and impact

Risk is the product of likelihood and impact on a five-point scale (1 to 25). Products of 20 and above are critical, 12 to 19 high, 6 to 11 medium, 3 to 5 low and below 3 informational.

#LikelihoodImpact
1Rare: requires unusual conditions or insider accessNegligible: no data or service affected
2Unlikely: requires authentication and specific conditionsMinor: limited, non-sensitive data or degraded service
3Possible: reachable by an authenticated userModerate: some sensitive data or a single customer affected
4Likely: reachable from the network with little effortMajor: sensitive data of many customers or a key function affected
5Almost certain: reachable anonymously, trivially exploitableSevere: full system compromise, regulatory breach or financial loss

Each finding is mapped to the most specific CWE weakness the rule or engine reports; OWASP Top 10 (2021) categories and compliance clauses are derived from the CWE where the finding does not carry its own mapping, and are marked as derived. Confidence reflects the detection technique (taint path or structural match) and the model's assessment; a model can lower confidence but never dismiss a finding.
