# Detector evaluation: measured values

This page records what `tools/detector_eval.py` measured, with the corpus and the date. It is
a statement of what was observed on a small synthetic corpus, not a claim about real
repositories. Precision and recall are reported separately; the harness has no blended score.

The harness measures detector accuracy on labelled text. It is not the end-to-end leakage
metric M1 (`INSIGHTS.md` section 4.3), but a detector miss on this corpus predicts a canary
leak in the ledger, which is why the recall of high-confidence subtypes is gated in CI.

## How to run it

```text
uv run python tools/detector_eval.py --check --out-dir build/detector-eval
```

The command writes `report.md` and `report.json` and exits 1 when the union recall of any
subtype is below 1.0 for labels of `high` confidence. CI runs it in the `detector-eval` job on
the in-repository corpus only and keeps both files as a build artefact.

## What is scored

A predicted span matches a labelled span when both have the same subtype and the Jaccard overlap
of their UTF-8 byte ranges is at least 0.5; candidate pairs are taken in descending order of
overlap and each span is used once. An unmatched prediction is a false positive and an unmatched
label a false negative. The table reports true positives, false positives, false negatives,
precision, recall, F1 and the mean Jaccard overlap of the matched pairs.

Two kinds of row appear. The `union` rows are the resolved output of all detectors
(`resolve_overlaps`), which is what redaction uses, so they are the per-subtype figures. The
other rows score one detector on its own raw output, restricted to the subtypes it reported. A
raw detector reports overlapping spans that `resolve_overlaps` later merges, so its false
positives are higher than the union's; compare the two to see what the merge removes.

## Corpus `labelled`, measured on 2026-11-10

| property | value |
|---|---|
| source | `tests/fixtures/detect/corpus` (PII and domain-term cases) and `tests/fixtures/detect/secrets` (secret cases) |
| origin | synthetic: every secret-shaped and personal-data value is generated by `tests/support/synthetic.py` at load time |
| cases | 113 |
| distinct texts | 113 (no repeated text) |
| labelled spans | 77 |
| subtypes with a union row | 42 |

Union result over the whole corpus: 77 true positives, 1 false positive, 0 false negatives.
Recall is 1.000 for every subtype, including every subtype that has a `high`-confidence label.
The one false positive is the `email` detector reading `svc@db.internal` in the secret case
`negative/connection_no_password`, a database URL whose user is a service name. The secret
manifest labels secrets only, so that case carries no email label; whether the span should be
redacted is a judgement and the figure shows the labelling, not a defect. `email` precision is
therefore 0.500 on 1 true positive and 1 false positive. The labelled spans of
single subtypes number between 1 and 11 each, so any per-subtype ratio rests on very few
examples; read the counts beside the ratio.

## What this does not show

- The corpus is the one the detectors were developed against, so recall of 1.000 on it is an
  expected result and not evidence about unseen code. The external corpora below exist to
  measure that.
- No external corpus has been scored yet. `tools/fetch_eval_corpora.py` fetches a public dataset
  at a pinned commit and checksum and does not vendor it; the pins in `tools/eval_corpora.toml`
  are empty until a person has read the dataset's licence and recorded the checksum, and the
  fetch is refused until they are filled. Converting a fetched dataset to the `cases.jsonl`
  format that `--external NAME=DIR` reads is dataset-specific and is not done.
- `INSIGHTS.md` section 5.3 records a study in which leakage between benchmark splits inflated
  secret-detection accuracy. Every report states a corpus, its size and whether texts repeat so
  that a figure can be read with that in mind.
- The optional engines (Gitleaks, detect-secrets) and the name recogniser are not scored by the
  CI job, because they are not installed there. Their adapters are tested against recorded
  output.
