## How to read this document

**Evidence grades.** Every quantitative claim carries a grade so that implementers and paper authors know how hard they can lean on it:

- **[P]** peer-reviewed venue (title, authors and venue were re-resolved through Crossref, OpenReview, ACL Anthology or the publisher during the survey).
- **[A]** arXiv preprint (identity confirmed through the arXiv API; not peer reviewed at survey time).
- **[V]** vendor documentation or vendor-reported figures (self-interested; cite as such).
- **[B]** practitioner blog, incident write-up or independent hands-on test.

**Numbers.** A number appears here only if it was present in the verified research files. Where the survey recorded only a qualitative result ("drops markedly", "most names recovered"), this document keeps it qualitative. Do not invent a figure when turning an insight into an issue or a paper sentence; open the cited source.

**Naming: `RAW` is not `L0`.** `docs/ARCHITECTURE.md` section 6.1 defines `L0` as *nothing leaves the premises* (local engines or a local model only). Several papers and some survey notes use "L0" informally for *raw code sent to a hosted LLM with no privacy layer*. To avoid a dangerous ambiguity, this document calls that experimental arm **`RAW`**. `RAW` exists only in the evaluation harness, only on open-source benchmark code, and must never be a configurable product level.

**Hypotheses vs findings.** Section 3.2 (expected utility loss per level) and the novelty claim in section 10 are *hypotheses to be tested by E36 and E37*. They are marked as such.

## 0. The ten insights that shape the architecture

1. **LLM-only function-level detection is not a product; context-bearing hybrids are.** On cleanly labelled data, code models that scored about 68% F1 on Big-Vul fall to low single digits and GPT-4 is near chance at telling a bug from its patch ([PrimeVul](https://arxiv.org/abs/2403.18624) [P]). The same models become useful once a static analyser supplies candidates, paths and context ([IRIS](https://arxiv.org/abs/2405.17238): 27 to 55 of 120 real Java CVEs [P]). Deterministic analysis first, LLM second, is the evidence-backed pipeline order.
2. **A minimal slice is simultaneously the accuracy lever and the privacy lever.** CPG-guided slicing removed 67.84 to 90.93% of the code while *improving* F1 by 15 to 40% over baselines ([LLMxCPG](https://www.usenix.org/conference/usenixsecurity25/presentation/lekssays) [P]); [LLM4FPM](https://arxiv.org/abs/2411.03079) [A] and Snyk's [CodeReduce](https://arxiv.org/abs/2402.13291) [A] found the same direction for triage and fixing. Nobody has measured the privacy reading of those numbers. L3 as the default is justified, and the gap is ours to fill.
3. **Identifier renaming costs accuracy, but how much depends on model strength and on what is kept.** Verdicts can flip when only names change ([SecLLMHolmes](https://arxiv.org/abs/2312.12575) [P], [ALERT](https://arxiv.org/abs/2201.08698) [P]); strong 2026 models keep roughly 90% Pass@1 on obfuscated code ([Robustness and Trade-offs](https://arxiv.org/abs/2609.04220) [A, ISSRE 2026 per arXiv comments]); layout obfuscation sometimes helps detection ([systematic obfuscation study](https://arxiv.org/abs/2512.16538) [A]). Pseudonyms must therefore be neutral, consistent, kind-preserving, and must keep public API, source, sink and sanitiser names.
4. **The same capability that preserves utility under renaming is the attacker's capability.** Statistical and neural models recover a large share of stripped names (47.5% exact for [Context2Name](https://arxiv.org/abs/1809.05193) [A]; "a majority" for [JSNice](https://doi.org/10.1145/2676726.2677009) [P]); [DOBF](https://arxiv.org/abs/2102.07492) [P] is literally trained to undo L2. Privacy must be *measured by attack* (E37), never asserted by construction. General-purpose obfuscation is provably impossible ([Barak et al.](https://doi.org/10.1145/2160158.2160159) [P]), so the honest claim is "minimise and de-name, then measure".
5. **The LLM may add and rank findings; it may never silently delete one.** A plausible rationale is not proof of a false positive ([Evident](https://arxiv.org/abs/2606.15122) [A]); adversarial comments and PR metadata get real reviewers to wave through re-introduced CVEs ([contextual-bias injection](https://arxiv.org/abs/2603.18740) [A], [ALIBI](https://arxiv.org/abs/2607.24964) [A], [Checkmarx Zero](https://checkmarx.com/zero-post/bypassing-claude-code-how-easy-is-it-to-trick-an-ai-security-reviewer/) [B]). LLM "false positive" verdicts downgrade and annotate; deterministic evidence stays in the report.
6. **Comment and string neutralisation at L2+ is a security control, not only a privacy control.** Every byte of the client repository is attacker-controlled input to the triage model ([Greshake et al.](https://arxiv.org/abs/2302.12173) [P]). The triage call must be a *quarantined LLM*: no tools, no network, schema-constrained output, one finding per call ([CaMeL](https://arxiv.org/abs/2503.18813) [A], [design patterns](https://arxiv.org/abs/2506.08837) [A]). Robustness claims must rest on architecture, because published filter defences fell to adaptive attacks at above 90% success ([The Attacker Moves Second](https://arxiv.org/abs/2510.09023) [A]).
7. **Third-party engines are remote code execution on our host.** CodeRabbit was compromised through a repo-supplied `.rubocop.yml` that exposed the GitHub App private key for a million repositories ([Kudelski](https://kudelskisecurity.com/research/how-we-exploited-coderabbit-from-a-simple-pr-to-rce-and-write-access-on-1m-repositories) [B]); a trojanised [Trivy](https://github.com/aquasecurity/trivy) release (March 2026) led to the [LiteLLM PyPI compromise](https://docs.litellm.ai/blog/security-update-march-2026) [V]. Every engine runs sandboxed with no network, no secrets, pinned by digest, and repo-supplied tool configuration is ignored or allow-listed.
8. **Licences constrain the engine list more than technology does.** CodeQL's CLI may not analyse a bank's proprietary code; the Semgrep registry rules and the archived opengrep-rules cannot be redistributed or offered as a service; Brakeman, Bearer, SonarQube analyzers and SysReptor are source-available traps. Default stack: [tree-sitter](https://github.com/tree-sitter/tree-sitter) + [Opengrep](https://github.com/opengrep/opengrep) (subprocess) + own MIT rule pack + [Joern](https://github.com/joernio/joern) / [atom](https://github.com/AppThreat/atom) for slices, everything normalised to SARIF that never leaves the machine.
9. **Contractual privacy is weaker than it looks, which is the product's reason to exist.** Flagged prompts can be kept for up to two years even under ZDR ([Anthropic retention docs](https://platform.claude.com/docs/en/manage-claude/api-and-data-retention) [V]); a court order overrode OpenAI's deletion policy ([OpenAI statement](https://openai.com/index/response-to-nyt-data-demands/) [V]); newest frontier models on Bedrock require a retention mode ([AWS docs](https://docs.aws.amazon.com/bedrock/latest/userguide/data-retention.html) [V]); the managed Claude Code Review is unavailable to ZDR organisations ([docs](https://code.claude.com/docs/en/code-review) [V]). Security-review prompts are exactly what abuse classifiers flag. Whatever we send must be safe to find in a leaked log ([DeepSeek exposure](https://www.wiz.io/blog/wiz-research-uncovers-exposed-deepseek-database-leak) [B]).
10. **No surveyed system combines slicing, reversible pseudonymisation and a measured leakage metric for security review.** Competitors offer contracts (CodeRabbit, Semgrep Multimodal, Copilot), private deployment (Corgea, Tabnine, GitLab Duo Self-Hosted), L1-only redaction (the archived [CodeGate](https://github.com/stacklok/codegate)), or white-box-only obfuscation ([CodeCipher](https://arxiv.org/abs/2410.05797), [NOIR](https://arxiv.org/abs/2601.16354)). The research contribution is the privacy-utility curve itself; the headline slice of that curve is authorisation and business-logic flaws, where LLM reasoning helps most and renaming hurts most.

## 1. State of the art in LLM vulnerability detection

### 1.1 What fails

| Failure | Evidence | Consequence for CodeKavach |
|---|---|---|
| Function-level "is this vulnerable?" classification | Models at about 68% F1 on Big-Vul collapse to low single digits on de-duplicated, chronologically split data; GPT-4 near chance on vulnerable-vs-patched pairs ([PrimeVul](https://arxiv.org/abs/2403.18624) [P]). 16 LLMs over 5,000 samples average about 63% accuracy, better on locally decidable classes and worse where whole-program context is needed ([Khare et al.](https://arxiv.org/abs/2311.16169) [P]). | Never ship a "scan every function with an LLM" mode as the primary detector. Function-level F1 must not be the headline metric of the paper. |
| The task itself is ill-posed without context | Most "vulnerable" functions are only vulnerable given calling context, and benchmark samples usually lack it ([Top Score on the Wrong Exam](https://arxiv.org/abs/2408.12986) [P]). | The L3 payload is a context-bearing slice (path + guards + callee stubs), not a lone function. |
| Reasoning faithfulness and determinism | Non-deterministic answers, wrong reasoning, verdicts that flip when only function or variable names change, across 228 scenarios ([SecLLMHolmes](https://arxiv.org/abs/2312.12575) [P]). Models struggle with bounds and NULL checks and multi-step reasoning and rarely separate buggy from fixed versions ([To Err is Machine](https://arxiv.org/abs/2403.17218) [A]). Temperature 0 is not deterministic on shared inference servers ([Thinking Machines](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/) [B]). | Supply pre-computed facts (taint path, guards, sanitisers) instead of asking the model to derive them. Use repeated-run consistency as the confidence signal. Cache verdicts so that a re-scan of unchanged code is reproducible (invariant I5). |
| Localisation | Coarse questions (exists? which CWE?) work; root-cause and trigger-line localisation are poor ([VulDetectBench](https://arxiv.org/abs/2406.07595) [A]); agentic pipelines still localise poorly at statement level ([SecVulEval](https://arxiv.org/abs/2505.19828) [P]). | Line-level evidence in reports comes from the deterministic engines and the slice map, never from the model's own line numbers. |
| Scale | LLM accuracy is high on small snippets and degrades, with hallucination, as code size grows ([CASTLE](https://arxiv.org/abs/2503.09433): 250 C programs, 25 CWEs, 13 analysers, 10 LLMs [P]). At project scale, five LLM-based detectors on 222 known vulnerabilities and 24 live projects (385 warnings manually inspected) find unique bugs but with low recall, many false positives and high cost ([project-scale study](https://arxiv.org/abs/2601.19239) [A]). | Slice minimisation helps accuracy as well as privacy. Budget tokens per finding (E22, E24). |
| Small models and classical ML | DL detectors lose more than half their performance on realistic data because of duplicates and token shortcuts ([ReVeal](https://arxiv.org/abs/2009.07235) [P]); they overfit to vulnerability-unrelated features and fail under semantic-preserving transformations including renaming ([Risse and Boehme](https://www.usenix.org/conference/usenixsecurity24/presentation/risse) [P]). An agent driven by three Ollama-hosted open models could not replace Bandit ([study](https://arxiv.org/abs/2606.11672) [A]). | Air-gapped mode is also hybrid; an open-weight model is a triager, not a scanner. |
| Dataset quality | Large fractions of wrong labels and duplicates inflate results ([Croft et al.](https://arxiv.org/abs/2301.05456) [P]); near-perfect "golden features" for alert pruning came from label leakage ([Kang et al.](https://arxiv.org/abs/2202.05982) [P]). | Evaluation protocol in section 9: de-duplicate, split by project and time, report a trivial baseline. |

### 1.2 What works

| Pattern | Evidence | How CodeKavach uses it |
|---|---|---|
| Static analysis proposes, LLM infers specs and triages paths | [IRIS](https://arxiv.org/abs/2405.17238) [P]: CodeQL alone finds 27 of 120 real Java CVEs on CWE-Bench-Java; with GPT-4 inferring taint specs and filtering paths, 55, with a lower false-discovery rate. | Same split (E17 taint engine, E23 `triage` task), with OSS engines in place of CodeQL and a privacy layer in front. Spec inference for *public third-party APIs* needs no client code at all. |
| Graph-guided minimal slices | [LLMxCPG](https://www.usenix.org/conference/usenixsecurity25/presentation/lekssays) [P]: 67.84 to 90.93% code-size reduction, 15 to 40% F1 gain, robust to syntactic modification. [LLM4FPM](https://arxiv.org/abs/2411.03079) [A]: "precise and complete but minimal" context drives triage accuracy. [CodeReduce](https://arxiv.org/abs/2402.13291) [A]: analysis-driven reduction markedly improves fix accuracy. | E11 slice extraction is the core of L3. |
| Structured, decomposed triage prompts | [LLift](https://arxiv.org/abs/2308.00245) [P]: about 50% precision on nearly a thousand reports the static analyser could not decide, with no apparent missed bugs. [BugLens](https://arxiv.org/abs/2504.11711) [P]: about seven-fold precision gain on kernel taint findings by stepping through security impact and constraint checks. | Triage prompt asks three questions in order: is the sink security-relevant, are the path constraints satisfiable, is there an effective sanitiser. |
| SARIF alert as a structured contract plus CWE-specific guidance | [ZeroFalse](https://arxiv.org/abs/2510.02534) [A]: best models reach F1 of about 0.91 on OWASP Java Benchmark and 0.96 on OpenVuln across ten LLMs; reasoning-oriented models do best; CWE-specialised prompts help consistently. | This is the no-privacy upper bound for our triage evaluation. Prompt library is keyed by CWE (E23). |
| Agents as false-positive filters | [Sifting the Noise](https://arxiv.org/abs/2601.22952) [P, to appear]: best configuration cuts the OWASP Benchmark false-positive rate from over 92% to about 6.3%, but gains depend strongly on backbone model and CWE. | Report per CWE and per model. An agent with full repository access is the context upper bound that L3 slices compete with. |
| Industrial transfer to unseen private code | Tencent study on 433 labelled alarms: developers spend 10 to 20 minutes per alarm; hybrid LLM + static techniques remove the vast majority of false positives at high recall and low per-alarm cost ([ICSE-SEIP 2026](https://arxiv.org/abs/2601.18844) [P]). | Business-case numbers for the paper introduction; evidence that results transfer to code the model has never seen. |
| Path feasibility by solver, not by prose | [LLM4PFA](https://arxiv.org/abs/2506.10322) [A] and [LLMDFA](https://arxiv.org/abs/2402.10754) [P]: the LLM extracts constraints or synthesises small scripts; a solver decides. | Constraints, not code, are what the solver needs. This is an L4-compatible pattern (E27). |
| Demand-driven, function-at-a-time exploration | [RepoAudit](https://arxiv.org/abs/2501.18160) [P]: 40 true bugs in 15 projects at 78.43% precision for about 0.44 hours and 2.54 USD per project. [Vulnhuntr](https://github.com/protectai/vulnhuntr) follows the call chain from handler to sink by asking for more code. | The `needs_context` loop in the architecture. In CodeKavach each extra function is a *privacy decision*: metered, budgeted per level, written to the ledger, counted by the leakage metric. |
| Local knowledge injection | [Vul-RAG](https://arxiv.org/abs/2406.11147) [P] retrieves CVE knowledge (functional semantics, root cause, fix) and improves pairwise accuracy. [LLM4Vuln](https://arxiv.org/abs/2401.16185) [A] separates intrinsic reasoning from add-ons. | Retrieval is local and the knowledge is public, so richer prompts cost no extra leakage. It compensates for natural-language hints removed at L2. |
| Rule synthesis instead of code scanning | [KNighter](https://arxiv.org/abs/2503.09002) [P] has the LLM write checkers from public patches; a 2026 study finds LLM-written queries raise F1 well above stock suites and are far cheaper than whole-repo scanning ([query generation](https://arxiv.org/abs/2609.10412) [A]). | A zero-leakage workflow: the model sees public CVE text and emits a rule that runs locally. Candidate mode for E16 rule-pack growth. |
| Focused security framing | 150-developer experiment: telling reviewers to focus on security raises detection markedly; a long checklist adds nothing ([Braz et al.](https://arxiv.org/abs/2202.04586) [P]). A security-review study of seven LLMs found a reasoning-optimised open model ranked first and that commit messages, CoT guidance or a CWE list change results ([Yu et al.](https://arxiv.org/abs/2401.16310) [A]). | Short, CWE-focused prompts; prompt ablation in E36. Note the tension: commit messages help, yet they are attacker-controlled and stripped at L2+. That is a measurable utility cost. |
| Frontier agents find real bugs | [Big Sleep](https://projectzero.google/2024/10/from-naptime-to-big-sleep.html) [B] found an exploitable SQLite bug before release; [AIxCC](https://archive.aicyberchallenge.com/) finalists are open source. | Motivation only. These systems upload or mount the whole repository, which is the adoption blocker we target. |

### 1.3 The counterpoint we must respect

[Everything You Wanted to Know About LLM-based Vulnerability Detection](https://arxiv.org/abs/2504.13474) [A] (CORRECT: 2,000 vulnerable/patched pairs, 99 CWEs, 13 LLMs) argues that pessimistic results came from *context-deprived prompts*. [VulEval](https://arxiv.org/abs/2404.15596) [P] shows that adding the right callee/caller dependencies helps and that current retrievers often fetch the wrong ones. Minimisation therefore has a floor: below it, accuracy collapses. The evaluation must plot accuracy as a function of slice size, and the product must ship the metered `needs_context` loop rather than a fixed slice.

### 1.4 Design consequences

- Deterministic candidates first; LLM for triage, explanation, CWE classification and targeted discovery on hotspot slices (E17, E23).
- Give the model facts, not homework: the payload carries the taint path, guards found, sanitiser models matched and the engine's rule description, all in pseudonym space.
- One finding per call, schema-constrained verdict, free-text `analysis` field *first* in the schema because strict formats can suppress reasoning ([Let Me Speak Freely?](https://arxiv.org/abs/2408.02442) [P]).
- Verdict confidence = deterministic evidence strength x self-consistency across repeated runs ([alert adjudication study](https://arxiv.org/abs/2607.09979) [A]); "abstain when inconsistent" is a valid verdict.
- Every comment links to an authoritative rule (CWE, ASVS requirement), precision is preferred over volume, and the dashboard collects "not useful" feedback ([AutoCommenter](https://arxiv.org/abs/2405.13565) [P], [Tricorder](https://doi.org/10.1109/ICSE.2015.76) [P]: keep user-perceived false positives under about 10%; [Coverity](https://doi.org/10.1145/1646353.1646374) [P]: above roughly 30% tools get ignored).

## 2. Why hybrid beats LLM-only (and SAST-only)

### 2.1 Evidence

| Claim | Evidence |
|---|---|
| SAST alone misses most real vulnerabilities | Static C analysers missed 47 to 80% of 192 real vulnerabilities in 27 projects (1.15 MLoC); combining tools lowered the miss rate to 30 to 69% at about 15 percentage points more flagged functions ([Lipp et al.](https://doi.org/10.1145/3533767.3534380) [P]). Seven Java tools (chosen from 161) detected 12.7% of real-world vulnerabilities; the union still missed 70.9% although matching rules often existed ([Li et al.](https://doi.org/10.1145/3611643.3616262) [P]). For Node.js, the three best of nine tools together detect at most 57.6% of 957 advisories at 0.11% precision ([Brito et al.](https://arxiv.org/abs/2301.05097) [P]). |
| SAST precision is not the main problem everywhere | About 1.5 million test executions on a synthetic Java code base: high precision, poor recall, narrow vulnerability coverage ([Esposito et al.](https://arxiv.org/abs/2403.09219) [P]). |
| At commit level SAST is a prioritisation signal, not ground truth | On 815 vulnerability-contributing commits (319 vulnerabilities, 92 projects) a single tool warns in the vulnerable function for 52% of commits, at least 76% of warnings in vulnerable functions are irrelevant to the actual flaw, 22% of commits go undetected, yet warning-based prioritisation still speeds reviewers up ([Charoenwet et al.](https://arxiv.org/abs/2407.12241) [P]). |
| LLMs and SAST fail in opposite directions | 15 SAST tools vs 12 LLMs on Java, C and Python repositories: SAST has low detection with few false alarms, LLMs the reverse, and combining them improves the trade-off ([Zhou et al.](https://arxiv.org/abs/2407.16235) [A]). On 26 vulnerable Python repos (796 labelled entries including 120 false-positive traps) the best rule-based tool scored about a third of the best general LLM by recall-weighted F3 ([RealVuln](https://arxiv.org/abs/2604.13764) [A]; treat as indicative: targets are likely in training data and the top scanner is the authors' product). |
| Hybrids beat both | IRIS doubling CodeQL (section 1.2); ZeroFalse and Sifting the Noise on triage; LLMxCPG on slices. |
| Hybrids are cheaper | RepoAudit at 2.54 USD per project; query synthesis far cheaper than whole-repo LLM scanning ([study](https://arxiv.org/abs/2609.10412) [A]). Compare the managed Claude Code Review at an average 15 to 25 USD *per review* ([docs](https://code.claude.com/docs/en/code-review) [V]). |
| Hybrids are the only design that fits the privacy goal | An LLM-only scanner must see everything. A hybrid sees only what the deterministic stage selected, so disclosure volume is bounded by the candidate set and the slice policy. |
| The pattern holds beyond SAST | Secrets: regex candidates + local fine-tuned 8B model reaches F1 0.985 ([Secret Breach Detection](https://arxiv.org/abs/2504.18784) [A]). SCA: scanners on accurate SBOMs showed a 92.0% false-positive rate, mostly unreachable code; function-call analysis prunes 61.9% ([SBOM reality check](https://arxiv.org/abs/2511.20313) [A]). Nine SCA tools disagree by an order of magnitude on the same app (17 to 332 Maven, 32 to 239 npm; [Imtiaz et al.](https://arxiv.org/abs/2108.12078) [P]). |

### 2.2 Design rules that follow

1. **Multi-engine candidate generation** with SARIF normalisation and de-duplication (E14, E21). Union recall beats any single tool, and engine disagreement is itself a triage feature.
2. **The LLM also looks where SAST is silent.** Because misses dominate, the `discover` task runs on *hotspot slices* that the deterministic stage marks as security-relevant but unflagged (entry points, authorisation checks, crypto, deserialisation, file and process APIs). This is budgeted separately and reported separately, since its precision will be lower.
3. **No silent suppression.** An LLM "false positive" verdict sets `status=llm_dismissed`, lowers rank and records a SARIF `suppression` with justification; the finding remains in the machine-readable output and in an appendix. Only a deterministic check (sanitiser model, unreachable path proof) may remove a finding ([Evident](https://arxiv.org/abs/2606.15122) [A]).
4. **No anchoring.** Present candidates neutrally ("assess whether ...") and do not pass the engine's severity, a prior tool's verdict, author names, PR titles or commit messages to the model; halo, framing and anchoring effects were shown across eight LLMs and three languages ([Words Speak Louder Than Code](https://arxiv.org/abs/2606.30587) [A]). Run the anchoring ablation in E36.
5. **Sanitiser recognition belongs to the taint engine's models**, not to the model's reading of a function called `sanitize()`; a fake sanitiser with a reassuring comment produced a clean report in practice ([Checkmarx Zero](https://checkmarx.com/zero-post/bypassing-claude-code-how-easy-is-it-to-trick-an-ai-security-reviewer/) [B]).
6. **Every LLM claim is anchored to a local artefact** (file, line range, snippet hash, rule id, taint path). Findings that cannot be anchored after de-pseudonymisation are dropped as hallucinations; fabricated AI reports with invented functions are what overwhelmed curl's security intake ([Stenberg](https://daniel.haxx.se/blog/2025/07/14/death-by-a-thousand-slops/) [B]).

## 3. Obfuscation, renaming and LLM accuracy

### 3.1 What is known

| Observation | Evidence |
|---|---|
| Names are a real information channel for models | Stripping names with semantics-preserving transformations clearly lowers summarisation and, unexpectedly, execution-prediction scores ([When Names Disappear](https://arxiv.org/abs/2510.03178) [A], releases ClassEval-Obf). CodeBERT-family performance depends heavily on meaningful names, and *misleading* names hurt more than *meaningless* ones ([Wang et al.](https://arxiv.org/abs/2307.12488) [P]). |
| Renaming alone can flip a vulnerability verdict | [SecLLMHolmes](https://arxiv.org/abs/2312.12575) [P] (function, variable and library-function renaming); [ALERT](https://arxiv.org/abs/2201.08698) [P] flips CodeBERT/GraphCodeBERT vulnerability predictions by natural-looking renames; on a 5,000-sample C/C++ benchmark detectors with 70%+ clean recall kept as little as 0.12% of detections under all behaviour-preserving attack variants, and adversarial strings tuned on a 14B surrogate transferred to GPT-4o ([evasion study](https://arxiv.org/abs/2602.00305) [A]). |
| Not all obfuscation is equal | 19 techniques in three classes (layout, data-flow, control-flow) across 15 LLMs and two agents: layout-level changes (what L2 does) are mostly benign and sometimes *raise* detection; control-flow transformations are destructive ([systematic study](https://arxiv.org/abs/2512.16538) [A]). LLMs explain ordinary code well and degrade markedly on heavier obfuscation ([Fang et al.](https://www.usenix.org/conference/usenixsecurity24/presentation/fang) [P]). |
| Model capability dominates | Seven code LLMs on obfuscated C++, Go, Java, JavaScript: strong models keep roughly 90% Pass@1; asking the model to de-obfuscate first often does not help ([Wen et al.](https://arxiv.org/abs/2609.04220) [A, ISSRE 2026 per arXiv comments]). General-purpose LLMs beat code-specialised ones on 250 obfuscated Java programs, across 13 models ([The Code Barrier](https://arxiv.org/abs/2504.10557) [A]). Stronger models tolerate far more redaction, and LLMs are poor at predicting what they actually need ([data minimisation for prompts](https://arxiv.org/abs/2510.03662) [P]). |
| Slicing plus renaming can preserve accuracy | LLMxCPG reports robustness to renaming and other semantic-preserving edits on its slices ([paper](https://www.usenix.org/conference/usenixsecurity25/presentation/lekssays) [P]). |
| String context survives when identifiers do not | [StringGroup/Secretron](https://arxiv.org/abs/2608.04523) [A]: keeping about a third of the context (string literals) preserves most signal for secret detection, 98.74% F1 on SecretBench, robust under obfuscation. |
| Natural language misleads models | Misleading comments, prints and identifiers cause large drops because models trust text over semantics ([CodeCrash](https://arxiv.org/abs/2504.14119) [P]); poisoned identifier names survived LLM de-obfuscation in every baseline run of a 192-run case study ([Guzmán Lorenzo](https://arxiv.org/abs/2604.04289) [A], one model family only). |
| Benchmarks leak labels through names | Juliet encodes ground truth in `bad`, `goodG2B`, CWE numbers in file names and comments. Renaming removes contamination as a side effect, so L2 results on Juliet and OWASP Benchmark may be *more honest* than raw results. |

### 3.2 Expected utility loss per privacy level (hypotheses for E36)

The vocabulary in the second column follows [ISO/IEC 20889](https://www.iso.org/standard/69373.html) so that the paper describes the ladder in standard terms.

| Level | Transformation (ISO 20889 term) | Expected effect on detection and triage | Confidence | Basis |
|---|---|---|---|---|
| `RAW` (evaluation only) | none | Upper bound. Reproduces ZeroFalse / IRIS-style numbers. | high | section 1.2 |
| L1 | masking / suppression of secrets and PII with typed placeholders | Negligible loss; possibly a small gain for CWE-798 and CWE-359 because the placeholder type states what was found. | L2 | pseudonymisation of identifiers, generalisation of literals, comment removal | Small loss for taint-style classes (injection, path traversal, SSRF, deserialisation, memory safety) where structure plus public API names carry the semantics. No surveyed paper reports accuracy for *reversible pseudonymisation on analysis-derived slices in a security-triage task*. The numbers in this table will be our own.

### 3.3 Mitigations (what to build into E09, E11, E23, E26)

1. **Keep what is public.** Language keywords, builtins, standard library, and well-known third-party API names stay in clear, because sources, sinks and sanitisers must remain recognisable (already in architecture step 4). [ProSan](https://arxiv.org/abs/2406.14318) [A] formalises the same idea as importance-vs-risk weighting. Caveat for the leakage side: the *set* of libraries in a slice fingerprints the stack ([DeGuard](https://doi.org/10.1145/2976749.2978422) [P] identifies third-party libraries under ProGuard), so the public allowlist is a disclosure that the leakage harness must count.
2. **Kind-preserving pseudonyms.** `fn_1`, `cls_2`, `var_3`, `param_4` preserve syntactic role with zero domain content. This is the architecture default and the right one.
3. **Analysis-derived role labels as a measured option.** Names such as `tainted_param_1`, `sink_arg_2`, `authz_check_3` are derived from the *local analysis result*, not from the original name, so they add task-relevant signal without revealing business vocabulary. When Names Disappear motivates role hints; this variant gets them without leaking. Treat as an ablation arm (kind-only vs analysis-role) in E26 and E36. Do **not** derive hints from the original identifier (for example by keeping suffixes such as `_id` or `_amount`) without measuring the leakage it causes.
4. **Neutral, never misleading.** A pseudonym must not accidentally be a meaningful word; misleading names hurt more than meaningless ones. Generate from a reserved alphabet and check against a dictionary.
5. **Consistent within a scan, unlinkable across scans.** Deterministic mapping under a per-scan salt keeps data flow intact and makes caching possible (I5). [ENISA](https://www.enisa.europa.eu/publications/pseudonymisation-techniques-and-best-practices) distinguishes deterministic, document-randomised and fully randomised policies; this is a tunable privacy-utility axis. Open design point: per-*request* randomisation lowers linkability across slices (section 4.2) but defeats the cache and may hurt multi-slice reasoning. Make it a policy knob and measure both settings.
6. **Type-preserving.** Keep declared types when they are public (`String`, `HttpServletRequest`, `int`); pseudonymise user-defined type names consistently with their declarations. Where SCIP or LSP facts are available ([SCIP](https://github.com/scip-code/scip), [multilspy](https://github.com/microsoft/multilspy)), a pseudonymised variable may carry its public supertype as an annotation.
7. **Shape-preserving literals.** SQL skeleton, format specifiers, path separators, URL scheme, regex structure and numeric magnitude class survive; domain words do not. Secretron's result suggests string shape carries much of the residual signal.
8. **Typed placeholders for redactions**, for example `<SECRET:aws_access_key:1>`, so that the model can still reason about CWE-798 without the value ([Preempt](https://arxiv.org/abs/2504.05147) two-category token model).
9. **Scope-correct renaming.** Use [LibCST](https://github.com/Instagram/LibCST) for Python and [ast-grep](https://github.com/ast-grep/ast-grep) rewrites over tree-sitter elsewhere, with SCIP or LSP resolution for cross-file symbols. Validate by re-parsing: AST isomorphic modulo leaf text (architecture step 5). Pin grammar versions; node-type changes silently break renaming rules.
10. **Compensate with local knowledge.** CWE-specific checklists (ZeroFalse) and Vul-RAG style retrieved knowledge go into the prompt from a local store. They are public text and cost no leakage.
11. **Summaries instead of bodies.** Out-of-slice callees become signature-only stubs plus an analysis-derived summary ("returns tainted if arg0 tainted"), following SDG summary edges ([Horwitz, Reps, Binkley](https://doi.org/10.1145/77606.77608) [P]) and LLMDFA's finding that function summaries suffice for inter-procedural reasoning.
12. **Thin slices by default, expand on demand.** [Thin slicing](https://doi.org/10.1145/1250734.1250748) [P] keeps only producer statements; guards and control dependences are added when the model answers `needs_context`. Optional second stage: shrink with [delta debugging](https://doi.org/10.1109/32.988498) [P] using "local-model or cached verdict unchanged" as the oracle, which yields an empirically minimal disclosure.
13. **Pick the model per level.** Prefer strong general-purpose or reasoning models at L2+; record per-model minimisation headroom. The policy engine (E25) may map "weaker local model" to a lower level (L1, nothing leaves anyway) and "frontier hosted model" to L3.
14. **Measure stability, not only accuracy.** Report the per-finding *verdict-flip rate* between `RAW`, L1, L2, L3 and a "complete resistance"-style score ([evasion study](https://arxiv.org/abs/2602.00305) [A]); aggregate F1 can hide symmetric flips.
15. **Strip benchmark tell-tales at every level**, including `RAW`, as an experimental control, and say so in the paper.

### 3.4 Where renaming hurts most: the headline slice of the curve

Authorisation and business-logic flaws ([API Security Top 10](https://api-security.owasp.org/editions/2023/en/0x11-t10/) BOLA/BFLA; CWE-862/863/639) are where LLM reasoning most plausibly beats pattern SAST, and where role and resource names (`isAdmin`, `tenantId`, `ownerId`) carry the semantics. Expect the steepest utility drop here. Two candidate mitigations to evaluate: (a) analysis-derived labels for *framework-recognised* authorisation constructs (decorators, annotations, middleware), which are public API and can stay in clear; (b) a client-approved **keep-list of generic security vocabulary** (`admin`, `owner`, `tenant`, `role`) that the egress guard allows. Option (b) is a deliberate, logged disclosure and must be off by default.

## 4. Attacker model for the privacy layer and candidate leakage metrics

### 4.1 Adversaries

| Id | Adversary | Capability | Evidence that it is realistic |
|---|---|---|---|
| A1 | Honest-but-curious LLM provider | Sees every payload and response, over time, keyed to the customer account. Runs any model over them. | Providers retain by default for about 30 days ([Anthropic](https://platform.claude.com/docs/en/manage-claude/api-and-data-retention), [OpenAI](https://developers.openai.com/api/docs/guides/your-data), [Azure](https://learn.microsoft.com/en-us/azure/foundry/responsible-ai/openai/data-privacy) [V]); free-tier Gemini content may be used for product improvement and read by human reviewers ([terms](https://ai.google.dev/gemini-api/terms) [V]). |
| A2 | Whoever obtains the provider's logs: breach, insider, legal process, abuse-review staff | Same data as A1, possibly years later. | Unauthenticated DeepSeek database with over a million log lines including chat history and API keys ([Wiz](https://www.wiz.io/blog/wiz-research-uncovers-exposed-deepseek-database-leak) [B]); NYT preservation order overrode deletion policy for non-ZDR traffic ([OpenAI](https://openai.com/index/response-to-nyt-data-demands/) [V]); classifier-flagged inputs kept up to 2 years even under ZDR ([Anthropic](https://platform.claude.com/docs/en/manage-claude/api-and-data-retention) [V]). Exploit-like code and secrets are what such classifiers flag. |
| A3 | Future users of a model trained on the data | Extraction prompts against a model that memorised payloads. | Training-data extraction ([Carlini et al.](https://arxiv.org/abs/2012.07805) [P]); code models memorise ([Al-Kaswan et al.](https://arxiv.org/abs/2312.11658) [P]); Copilot and CodeWhisperer emitted thousands of valid-format secrets, some live ([HCR](https://arxiv.org/abs/2309.07639) [P]; [CodexLeaks](https://www.usenix.org/conference/usenixsecurity23/presentation/niu) [P]). This is why L1 is mandatory and cannot be disabled, even for self-hosted models that may later be fine-tuned. |
| A4 | Gateway or aggregator between us and the provider | Full request bodies. | [OpenRouter](https://openrouter.ai/docs/quickstart) documents per-upstream logging policies; SaaS observability proxies see everything. Treat as a separate trust boundary; the policy engine must name it. |
| A5 | Network observer | Packet sizes and timing of encrypted streams. | Response reconstruction from token lengths ([keylogging attack](https://arxiv.org/abs/2403.09751) [P]); topic classification across providers ([Whisper Leak](https://arxiv.org/abs/2511.03675) [A]). Mitigation: no streaming for triage calls, optional padding. |
| A6 | Co-tenant exploiting shared prompt caches | Timing probe: "has someone sent this prefix?" | Global cross-user cache sharing found at seven API providers at study time ([Gu et al.](https://arxiv.org/abs/2502.07776) [A]); vLLM documents a prefix-cache timing channel and per-tenant `cache_salt` ([vLLM security](https://docs.vllm.ai/en/latest/usage/security/) [V]). Rule: the cached prefix contains only CodeKavach's public rubric; client material goes after the cache breakpoint. |
| A7 | Insider with access to the local ledger or vault | Reads stored payloads or the mapping. | Architecture invariants I3 and the encrypted ledger. Outside the leakage metric, inside the threat model. |

**Auxiliary knowledge to assume for A1/A2:** all public code and documentation (for nearest-neighbour matching and library fingerprinting), strong deobfuscation models, the public CodeKavach source including the pseudonym scheme and allowlist (Kerckhoffs), and the *identity of the account holder*. The last point matters: if the bank's own API key is used, the provider already knows who the client is; if the auditing firm's key is used, client identity becomes something slices can leak. The report's privacy attestation should state which case applied.

**Adversary goals:** G1 recover secrets and PII; G2 recover original identifiers; G3 reconstruct business logic or infer business domain, product and purpose; G4 re-identify the client, the project, an open-source component or an individual developer; G5 link slices into a larger picture of the code base.

This is the pseudonymisation-domain model of [EDPB Guidelines 01/2025](https://www.edpb.europa.eu/public-consultations/guidelines-012025-on-pseudonymisation_en): the local vault is the "additional information", the provider is outside the domain, and effectiveness is judged against defined attackers. [LINDDUN](https://linddun.org/) supplies the threat categories (Linking, Identifying, Data disclosure, Non-compliance); [MITRE ATLAS](https://atlas.mitre.org/) and [NIST AI 100-2 E2025](https://csrc.nist.gov/pubs/ai/100/2/e2025/final) supply the attack terminology; [NIST SP 800-188](https://csrc.nist.gov/pubs/sp/800/188/final) is the precedent for measuring privacy by running a motivated-intruder attack. Results should also be reported against the three-risk test of [Article 29 WP Opinion 05/2014](https://ec.europa.eu/justice/article-29/documentation/opinion-recommendation/files/2014/wp216_en.pdf) (singling out: M5; linkability: M8; inference: M2 and M4), which is the vocabulary data-protection officers use, and the re-identification attacker follows [Narayanan and Shmatikov](https://doi.org/10.1109/SP.2008.33) [P] in holding all public code as auxiliary information.

### 4.2 Attacks the leakage harness must implement (E37)

| Attack | Prior art to reuse | Note |
|---|---|---|
| **Identifier recovery** from usage context | [JSNice](https://doi.org/10.1145/2676726.2677009) [P] (majority of minified JS names); [Context2Name](https://arxiv.org/abs/1809.05193) [A] (about 47.5% of minified identifiers on a 150k-file corpus); [VarNaming](https://arxiv.org/abs/1711.00740) [P] (task definition); [DOBF](https://arxiv.org/abs/2102.07492) [P] (MIT code, trained to restore all names in a function: the primary learned adversary); [DIRE](https://arxiv.org/abs/1909.09029) [P] and [DIRTY](https://www.usenix.org/conference/usenixsecurity22/presentation/chen-qibin) [P] for C/C++; [JsDeObsBench](https://arxiv.org/abs/2506.20170) [P] for JS/TS; a prompted frontier LLM ([humanify](https://github.com/jehna/humanify) shows the recipe). | Split by project and de-duplicate, otherwise recovery rates are inflated by shared library code (DIRE's lesson). Score exact match and semantic closeness separately: recovering `amount` for `transferAmount` is a partial leak. |
| **Structure-based re-identification** | Nearest-neighbour search of the pseudonymised slice against a public corpus with [UniXcoder](https://arxiv.org/abs/2203.03850) [P] embeddings ([CodeSearchNet](https://arxiv.org/abs/1909.09436) as corpus); library fingerprinting as in DeGuard; function names are largely inferable from structure ([code2vec](https://arxiv.org/abs/1803.09473) [P]). | For open-source or vendored components the attacker simply looks the code up. Do not send vendored/third-party code at all: the deterministic stage should identify it (SCA, Retire.js-style signatures) and exclude it from slices. |
| **Stylometric attribution** | [Caliskan-Islam et al.](https://www.usenix.org/conference/usenixsecurity15/technical-sessions/presentation/caliskan-islam) [P] (very high accuracy over hundreds to more than a thousand authors from lexical, layout and AST features); zero-shot LLM attribution reaching roughly two-thirds accuracy from a single reference sample over 500 C++ and 686 Java authors ([paper](https://arxiv.org/abs/2501.08165) [A]). | Layout features vanish if we pretty-print from the AST; AST-shape features do not. Optional normalising pretty-printer at L2+; measure residual attribution. Producing a k-anonymous program is not computable in general, and normalisation, style imitation and obfuscation all failed against an attacker who knows the transformation ([Horlboge et al.](https://arxiv.org/abs/2208.12553) [P]), so report this as a measured reduction and keep the attacker adaptive. |
| **Business-domain and attribute inference** | [Beyond Memorization](https://arxiv.org/abs/2310.07298) [P] (LLMs infer personal attributes from innocuous text at near-human accuracy; anonymisers do not stop it). Code analogue: ask an attacker LLM for business domain, organisation type, product and purpose of each slice; score top-k against ground truth. [LLM de-anonymisation pipeline](https://arxiv.org/abs/2602.16800) [A] is the template: feature extraction, embedding retrieval, LLM verification. | This is the attack bank clients care about most and the one nobody has measured for code. |
| **Logic reconstruction** | Attacker LLM de-obfuscates and rewrites the slice; compare with the original using [CodeBLEU](https://arxiv.org/abs/2009.10297) components and [CodeBERTScore](https://arxiv.org/abs/2302.05527) [P]. | The data-flow component of CodeBLEU *should* stay high (that is utility); the n-gram and name components should drop. Report components separately. |
| **Aggregation across slices** | LINDDUN *Linking*: deterministic pseudonyms let a provider stitch slices from one scan into call graphs. | Metric: fraction of repository functions, files and distinct call edges disclosed per scan and cumulatively per engagement; success of a re-assembly attack that joins slices on shared pseudonyms. Controls: aggregation budget in the egress guard (architecture step 6), per-request salts as a policy option, signature-only stubs. |
| **Embedding or vector inversion** (relevant to any "we only send vectors" idea and to L4) | [vec2text](https://arxiv.org/abs/2310.06816) [P] recovers most short inputs exactly; [Language Model Inversion](https://arxiv.org/abs/2311.13647) [P] reaches BLEU 59, token F1 78 and 27% exact prompt recovery on Llama-2 7B from next-token probabilities. | Embeddings are not a privacy boundary. L4 must send symbolic facts over pseudonyms, never embeddings of raw code. Note also that retrieval over a client repo through a hosted embedding API would disclose the whole repo. |
| **Adaptive adversarial loop** | [LLMs are Advanced Anonymizers](https://arxiv.org/abs/2402.13846) [P]: attacker infers, anonymiser edits, repeat until inference fails. | Doubles as an optional product feature: run a *local* attacker model against the outgoing slice and tighten the transformation before sending (E26). |

### 4.3 Candidate leakage metrics

| Id | Metric | Definition | Target / use |
|---|---|---|---|
| M1 | Canary leak rate | Planted secrets and PII found in any ledger payload. Ground truth from [SecretBench](https://arxiv.org/abs/2303.06729) (97,479 candidates, 15,084 true secrets, 818 repos; access needs a data-protection agreement, so request early) and [FPSecretBench](https://arxiv.org/abs/2307.00714). | Must be zero; CI gate (E28). A missed secret is by definition a leak to the provider. |
| M2 | Identifier recovery | Exact-match accuracy, token-level F1, character error rate (DIRTY's metrics) and embedding similarity of recovered vs original names, per attacker, per identifier kind. | Headline privacy axis for L2 vs L3. |
| M3 | Reconstruction similarity | CodeBLEU (four components reported separately) and CodeBERTScore between original slice and attacker's reconstruction. | Shows that structure is retained (utility) while naming is not (privacy). |
| M4 | Domain / logic inference | Top-k accuracy of attacker-LLM guesses for business domain, application type, organisation type; rubric-scored similarity between an attacker-written summary and a ground-truth summary. | Headline business-logic axis. Needs a benchmark with domain labels (for example [vuln-bank](https://github.com/Commando-X/vuln-bank), [AltoroJ](https://github.com/HCL-TECH-SOFTWARE/AltoroJ), plus non-banking controls). |
| M5 | Re-identification / k-anonymity | Rank of the true source among nearest neighbours in a public corpus; a slice is "k-anonymous" if at least k corpus slices are structurally indistinguishable ([Sweeney](https://doi.org/10.1142/S0218488502001648) [P]). | Warns when a slice embeds a recognisable fingerprint. |
| M6 | Authorship attribution | Accuracy of stylometric and LLM attribution on pseudonymised slices vs originals. | Secondary; supports the pretty-printing option. |
| M7 | Disclosure volume | Tokens, lines, functions and files sent; percentage of repository disclosed; number of `needs_context` expansions; all per finding, per scan, cumulative. | Cheap, always-on, shown in the report's privacy attestation. The LLMxCPG 68 to 91% reduction is the external reference point. |
| M8 | Linkability | Success of cross-request linking under each pseudonym policy. | Evaluates the ENISA policy axis. |
| M9 | One-guess success (min-entropy leakage) | Change in the adversary's probability of guessing a hidden attribute in one try ([Smith](https://doi.org/10.1007/978-3-642-00596-1_21) [P]). | Principled framing for M2 and M4; preferable to Shannon mutual information. |
| U1 | Utility (paired with every M) | Precision, recall, F1, pairwise accuracy, verdict-flip rate (section 9). | Privacy-utility curves follow [PAPILLON](https://arxiv.org/abs/2410.17127) [P]: quality preserved vs leakage rate. |

Formal anchors for the paper: keyed format-preserving pseudonyms give a cryptographic argument for the *naming channel* only ([Preempt](https://arxiv.org/abs/2504.05147) [P]; [NIST SP 800-38G](https://csrc.nist.gov/pubs/sp/800/38/g/upd1/final): FF1 only, and short identifiers fall below the safe domain size, so an HMAC-derived token plus the encrypted local vault is the default). For everything else there is an inherent trade-off ([No Free Lunch theorem](https://arxiv.org/abs/2405.20681) [P]) and an impossibility result for hiding logic ([Barak et al.](https://doi.org/10.1145/2160158.2160159) [P]). Word-level differential privacy is a poor fit for code: it breaks syntax and offers weak protection ([Mattern et al.](https://arxiv.org/abs/2205.02130) [P]).

### 4.4 What the privacy layer cannot hide (state it in the report)

- The algorithmic structure of whatever is sent. Minimisation is the only control.
- The technology stack, through kept public API names.
- That a particular vulnerability class is suspected at a particular kind of sink (the question itself leaks).
- Timing and volume of the audit.
- Anything in a file the policy engine was never told is sensitive; hence `never-send` path rules and the domain-term dictionary (E08, E25).

## 5. Engine selection matrix

**Verdict legend.** **OK**: permissive licence, may be bundled in the MIT distribution and Docker image (import or subprocess as stated). **CAVEAT**: usable under a stated condition (subprocess only, client-installed, research only, staleness). **AVOID**: do not bundle, do not depend on, do not present as current.

**Integration rule for every copyleft engine (LGPL, GPL, AGPL, MPL):** separate process, communicate through files (SARIF/JSON), never import, never copy code, never link. AGPL tools are additionally kept out of any *hosted* image.

**Build tiers.** Audits of third-party bank code frequently arrive without a working build. The plugin contract (E14) therefore declares a tier per engine: **no-build** (works on source, tolerant of errors) or **build** (needs compilation, bytecode, a type-checkable project or a compile database). When a build-tier engine cannot run, the scan degrades gracefully and the report's scope and limitations section says so ([Coverity's lesson](https://doi.org/10.1145/1646353.1646374): getting arbitrary builds to parse is the hard part).

### 6.2 Standing policy (enforce in CI, E01 and E40)

1. **Process boundary** for every LGPL/GPL/AGPL/MPL engine; adapters exchange SARIF or JSON files only.
2. **No vendoring** of third-party rules, benchmark code or report PDFs; fetch scripts with pinned commit hashes and checksums instead.
3. **Licence manifest**: every engine adapter, rule pack, model and dataset declares SPDX id, distribution mode (`bundled`, `client-installed`, `evaluation-only`) and hosted-use flag. The Docker build for the hosted edition fails if a `hosted=false` item is present.
4. **Self-scan**: run [ScanCode Toolkit](https://github.com/aboutcode-org/scancode-toolkit) and an SBOM over our own image in CI.
5. **Provenance for reused code**: a commit hash and licence note in the file header, checked in review (AGENTS.md checklist).
6. **Compliance annex wording** explains to the client which optional engines they enabled under their own licences (CodeQL, Brakeman, Semgrep registry rules).

## 7. Threats to the tool itself

Write the threat model (`docs/THREAT_MODEL.md`, E40) against [OWASP Top 10 for LLM Applications 2025](https://genai.owasp.org/llm-top-10/), the [Agentic Top 10 (2026)](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/), MITRE ATLAS and NIST AI 100-2. The UK NCSC position is the framing sentence: prompt injection cannot be fixed once and for all the way parameterised queries fixed SQL injection; manage it through constrained design ([NCSC](https://www.ncsc.gov.uk/blog-post/prompt-injection-is-not-sql-injection) [B]).

| Threat | Evidence | Required controls | Epics |
|---|---|---|---|
| **Prompt injection from reviewed code** (LLM01): comments, strings, identifiers, file names, PR titles, commit messages, AI-assistant rules files | [Indirect prompt injection](https://arxiv.org/abs/2302.12173) [P]; [ALIBI](https://arxiv.org/abs/2607.24964) [A] iteratively refines false comments until the detector misses a real bug; [contextual-bias injection](https://arxiv.org/abs/2603.18740) [A] got real pipelines to pass re-introduced CVEs in almost all tested cases; [Checkmarx Zero](https://checkmarx.com/zero-post/bypassing-claude-code-how-easy-is-it-to-trick-an-ai-security-reviewer/) [B]; [Comment and Control](https://oddguan.com/blog/comment-and-control-prompt-injection-credential-theft-claude-code-gemini-cli-github-copilot/) [B] stole API keys and `GITHUB_TOKEN` from three vendors' review actions; Anthropic's own [security-review action](https://github.com/anthropics/claude-code-security-review) states it is not hardened against injection. | Quarantined LLM: no tools, no network, no file access, typed output only ([dual LLM](https://simonwillison.net/2023/Apr/25/dual-llm-pattern/), [CaMeL](https://arxiv.org/abs/2503.18813), [lethal trifecta / Rule of Two](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)). Comments and docstrings removed and strings generalised at L2+. Never interpolate PR, issue or commit metadata into prompts. [Spotlighting](https://arxiv.org/abs/2403.14720) [A] with randomised per-request delimiters. One finding per call (LLM map-reduce) so that one poisoned file cannot influence other verdicts. Deterministic findings cannot be suppressed by the model. [CodeSentinel](https://arxiv.org/abs/2606.19235) [A] (about 0.80 node-level F1) is the selective-detection baseline to compare "strip everything" against. | E23, E24 |
| **Hidden Unicode** | [Trojan Source](https://arxiv.org/abs/2111.00169) [P]; [Unicode Tag smuggling](https://embracethered.com/blog/posts/2024/hiding-and-finding-text-with-unicode-tags/) [B]; [Rules File Backdoor](https://www.pillar.security/blog/new-vulnerability-in-github-copilot-and-cursor-how-hackers-can-weaponize-code-agents) [B]. | Before parsing and before prompt construction: detect and normalise bidi controls, zero-width and Unicode Tag characters; raise them as findings rather than stripping silently; scan `.cursor/rules`, `.github/copilot-instructions.md`, `AGENTS.md`, `CLAUDE.md`, `.windsurfrules`. | E06, E16, E24 |
| **Malicious repository executes code on the scanner** | [CodeRabbit RCE](https://kudelskisecurity.com/research/how-we-exploited-coderabbit-from-a-simple-pr-to-rce-and-write-access-on-1m-repositories) [B] through a repo-supplied linter config; builds, `pip install`, Gradle/Maven, npm scripts and git hooks are all code execution. | Every engine in a locked-down container: no network, no secrets, read-only source mount, resource limits. Ignore or allow-list repo-supplied tool configuration (ESLint, RuboCop, Semgrep rules, Psalm plugins). Build-tier engines run only inside the sandbox and only when the policy allows a build. The reviewer never executes client code outside it. GitHub App private key lives in a separate signing service, never in the scanner's environment. | E14, E15, E34, E40 |
| **Archive and ingest abuse**: decompression bombs, path traversal and symlink escape in archives, huge or deeply nested files, pathological inputs for parsers and regexes, submodules and LFS pointers that trigger network fetches | Non-recursive zip bombs reach expansion ratios in the tens of millions, so a nested-archive check is not enough ([Fifield, WOOT 2019](https://www.usenix.org/conference/woot19/presentation/fifield) [P]); crafted entry names write outside the extraction root ([Zip Slip](https://github.com/snyk/zip-slip-vulnerability) [B]); `git clone --recursive` of a crafted repository executed attacker code through a submodule and symlink pair ([CVE-2024-32002](https://github.com/git/git/security/advisories/GHSA-8h77-4q3w-gfgv) [V]); super-linear regular expressions are common in real code and rule sets ([Davis et al.](https://doi.org/10.1145/3236024.3236027) [P]). ## 8. Reporting conventions distilled from public audit reports

Sources read during the survey: [Trail of Bits cURL review 2022](https://github.com/trailofbits/publications/blob/master/reviews/2022-12-curl-securityreview.pdf), [X41 Git audit 2023](https://x41-dsec.de/static/reports/X41-OSTIF-Gitlab-Git-Security-Audit-20230117-public.pdf), Cure53 curl audit 2016 ([Cure53 publications](https://cure53.de/#publications)), [NCC Group public reports](https://www.nccgroup.com/research/?category=public-reports), [Doyensec Teleport report with retesting](https://www.doyensec.com/resources/Doyensec_Gravitational_Teleport_Report_Q32022_WithRetesting.pdf), [OWASP WSTG chapter 5](https://github.com/OWASP/wstg/blob/master/document/5-Reporting/01-Reporting_Structure.md), [PTES Reporting](http://www.pentest-standard.org/index.php/Reporting), [PCI Penetration Testing Guidance v1.1](https://listings.pcisecuritystandards.org/documents/Penetration-Testing-Guidance-v1_1.pdf), and [CERT-In Comprehensive Cyber Security Audit Policy Guidelines v1.0](https://www.cert-in.org.in/PDF/Comprehensive_Cyber_Security_Audit_Policy_Guidelines.pdf) section 16. Corpora for further sampling: [public-pentesting-reports](https://github.com/juliocesarfort/public-pentesting-reports), [Trail of Bits publications](https://github.com/trailofbits/publications), [OSTIF audits](https://ostif.org/audits/), [Quarkslab public-reports](https://github.com/quarkslab/public-reports). Link to reports; do not redistribute them.

### 8.1 Canonical section list (E30)

0. Cover with classification marking (PUBLIC / CONFIDENTIAL) repeated on every page; firm boilerplate.
1. Document control: version table (draft/final, date, author, change), distribution list, reviewers, sign-off block.
2. Notices: copyright and distribution; point-in-time and coverage disclaimer (time-boxed, not exhaustive, tool limitations).
3. Executive summary for non-technical readers: objective, overall posture, key findings in business terms, counts by severity (chart), strategic recommendations. CERT-In requires it to be written for the board or top management.
4. Dashboard / project summary on one page: target, version or commit, engagement type, team, effort, dates, totals by severity and by CWE (X41 style).
5. Scope, goals and targets: repositories, commits, languages, in and out of scope, assumptions.
6. Methodology and coverage: manual vs automated techniques, tools **and versions**, what was and was not covered, recommended further testing, limitations. Cite [NIST IR 8397](https://csrc.nist.gov/pubs/ir/8397/final) for what the deterministic stage covers and give honest out-of-scope wording for fuzzing and DAST. **CodeKavach addition:** privacy attestation (level used per path, provider and retention terms, disclosure-volume metrics M7, ledger hash).
7. Rating methodology *defined inside the report*: severity scale, second axis (difficulty / exploitability / likelihood), CVSS usage and nomenclature, CWE mapping rule.
8. Codebase maturity evaluation by control family with rating and rationale (Trail of Bits style); optional.
9. Summary of findings table: ID, title, category, severity, status.
10. Detailed findings (template below).
11. Informational and hardening notes kept separate from vulnerabilities (X41 "informational notes", Cure53 "miscellaneous issues"). Natural home for LLM-suggested hardening and for `llm_dismissed` candidates.
12. Remediation roadmap and retest results (PTES "strategic roadmap"); SSVC-style action and SLA column.
13. Appendices: category and severity definitions, tool output, analysis details, artefact hashes / versions / timestamps, compliance mapping annex, SBOM, data-source notices.

Offer two profiles: **full** (Trail of Bits / X41 weight) and **lean** (Cure53: introduction, scope, identified vulnerabilities, miscellaneous issues, conclusion). Offer an **assurance variant** organised around [ISACA ITAF](https://www.isaca.org/about-us/newsroom/press-releases/2020/isaca-updates-it-audit-framework-itaf) reporting elements for internal-audit readers.

### 8.2 Per-finding field list (union across firms; E02 domain model, E30)

`id` (stable, `PREFIX-NNN`; Cure53's `PROJECT-ROUND-NNN` survives retests) · `title` · `severity` · `difficulty_or_likelihood` (ToB: difficulty; NCC: impact and exploitability as separate axes) · `impact` · `cvss_v4_vector` · `cvss_v3_1_vector` · `epss` (CVE-backed only) · `cwe_id` · `owasp_top10_category` · `asvs_requirement` · `type_or_category` · `target_component` · `location_file_line` · `description` · `code_evidence_snippet` (text, highlighted with [Pygments](https://pygments.org/), never screenshots; secrets masked even in the local report, as WSTG instructs) · `taint_path_or_code_flow` · `exploit_scenario` · `business_impact` (**local only, never sent to the LLM**) · `recommendation_short_term` · `recommendation_long_term` · `references` · `status / retest_status` · `confidence` · `detected_by` (engine, rule, LLM) · optional audit "5 Cs" view: criteria, condition, cause, consequence, corrective action ([IIA Global Internal Audit Standards](https://www.theiia.org/en/standards/2024-standards/global-internal-audit-standards/) 14.3).

### 8.3 Rating conventions

- **CWE is the primary key**; derive everything else from data: CWE-1344 (Top 10:2021), CWE-1450 (Top 10:2025, still titled RC1 in CWE 4.20), CWE-1435 (2025 Top 25), [CWE-1400](https://cwe.mitre.org/data/definitions/1400.html) (one bucket per CWE for charts and per-category accuracy tables), [CWE-1003](https://cwe.mitre.org/data/definitions/1003.html) (shared vocabulary between SCA and SAST), CWE-1000 edges for hierarchical-match scoring. Enforce MITRE root-cause mapping guidance so that the model cannot default to CWE-20 or Pillar-level labels ([MITRE mapping guidance](https://cwe.mitre.org/documents/cwe_usage/guidance.html)); wrong-level CWE mapping is a measurable LLM error class.
- **Emit CVSS v4.0 and v3.1 vectors**; recompute scores locally from the vector; store per-metric rationale; label nomenclature honestly (CVSS-B vs CVSS-BE). GitHub's `security-severity` comes from the score. Derive AV/PR/UI deterministically from code context (entry-point type, auth decorators) and use LLM judgement only where needed ([LLM CVSS study](https://arxiv.org/abs/2504.10713) [P, workshop]).
- **Human sign-off on severity.** 196 CVSS users rate the same vulnerabilities inconsistently and change their own ratings months later ([Wunder et al.](https://arxiv.org/abs/2308.15259) [P]); evaluate LLM-assigned CVSS against an inter-rater band, not exact match.
- **EPSS only exists for CVEs.** CERT-In requires CVSS plus EPSS; for first-party findings document the substitute: membership of the [CWE Top 10 KEV Weaknesses](https://cwe.mitre.org/top25/archive/2025/2025_kev_list.html) plus an SSVC decision, and say so in the rating methodology.
- **Business context stays local.** [OWASP Risk Rating](https://owasp.org/www-community/OWASP_Risk_Rating_Methodology) business-impact factors and CVSS Environmental metrics live in a client-side asset profile that is never sent to the LLM: it is precisely the business context being protected.
- **Confidence is separate from severity** (CWSS's finding-confidence idea): deterministic evidence strength x LLM verdict consistency.
- **Compliance annex from data**: snapshot [OpenCRE](https://www.opencre.org/) (CC0) at build time as the offline crosswalk (ASVS, WSTG, NIST 800-53, SSDF, ISO 27001, PCI DSS); maintain a small local overlay for RBI, SEBI, CERT-In and DPDP clauses, which no public mapping covers. Build a **CERT-In profile** (CVSS + EPSS + CWE columns, artefact hash table, draft/final versioning, three-level sign-off, encrypted PDF) and note that [SEBI CSCRF](https://www.sebi.gov.in/legal/circulars/aug-2024/cybersecurity-and-cyber-resilience-framework-cscrf-for-sebi-regulated-entities-res-_85964.html) prescribes a close-to-identical observation table. Regulatory hooks for the bank story: [RBI IT Governance MD 2023](https://www.rbi.org.in/Scripts/BS_ViewMasDirections.aspx?id=12562), [RBI DPSC 2021](https://www.rbi.org.in/Scripts/BS_ViewMasDirections.aspx?id=12032), [RBI IT Outsourcing MD 2023](https://www.rbi.org.in/Scripts/BS_ViewMasDirections.aspx?id=12486), and the data-localisation circular [Storage of Payment System Data (2018)](https://www.rbi.org.in/Scripts/NotificationUser.aspx?Id=11244&Mode=0), which a bank's compliance team can be expected to raise against an LLM endpoint outside India. Audit teams that scope against [COBIT 2019](https://www.isaca.org/resources/cobit) get an optional objective-identifier column (REFERENCE.md section 10.2). Confirm clause numbers against the primary PDFs before quoting them (appendix A).

### 8.4 Rendering stack (E31), all licence-checked

One [Jinja2](https://github.com/pallets/jinja) (BSD-3) HTML template feeds both the HTML report and, through print CSS, [WeasyPrint](https://github.com/Kozea/WeasyPrint) (BSD-3) PDF: deterministic, air-gap friendly, no JavaScript so charts are pre-rendered SVG (Matplotlib). DOCX through [python-docx](https://github.com/python-openxml/python-docx) (MIT) and, as an optional extra, [docxtpl](https://github.com/elapouya/python-docx-template) (LGPL-2.1-only) for client-branded Word templates in the [Ghostwriter](https://github.com/GhostManager/Ghostwriter) manner. XlsxWriter for the findings register that GRC teams expect. ReportLab as the minimal-install fallback; Typst and Playwright as optional high-fidelity backends. SARIF export conforms to [GitHub's subset and limits](https://docs.github.com/en/code-security/reference/code-scanning/sarif-files/sarif-support) (10 MB gzip, 25,000 results per run of which the top 5,000 are kept) and must import cleanly into DefectDojo (CI test). GitHub issue sync is throttled and resumable: no more than 80 content-creating requests per minute and 500 per hour ([rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)); one parent issue per audit with sub-issues, idempotent through a hidden fingerprint marker; group low-severity findings. Private-repo code scanning needs paid GitHub Code Security, so degrade to Checks and PR comments.

### 9.2 Metrics

- **Detection and triage:** precision, recall, F1 per CWE (CWE-1400 buckets), per language, per level, per model; TPR/FPR and Youden index for OWASP Benchmark; **pairwise accuracy** (vulnerable vs patched) as the primary robustness-aware metric; false-positive reduction at fixed recall for triage; hierarchical CWE match; [VulDetectBench](https://arxiv.org/abs/2406.07595) task ladder to show which capabilities survive pseudonymisation.
- **Stability:** verdict-flip rate between levels; self-consistency across repeated runs; abstention rate.
- **PR / CI mode:** share of vulnerable changes flagged, warning precision, reviewer effort saved ([Charoenwet et al.](https://arxiv.org/abs/2407.12241) measures).
- **Slicer:** slice recall of ground-truth vulnerable statements and required context; slice size; number of `needs_context` expansions.
- **Severity:** CVSS vector agreement within an inter-rater band; per-metric accuracy.
- **Cost:** tokens, USD and wall time per finding and per KLoC (RepoAudit's 2.54 USD per project as an external reference).
- **Leakage:** M1 to M9 (section 4.3), always paired with a utility number.
- **Always report a trivial baseline** (all-positive, engine-severity-only) next to LLM results.

### 9.3 Baselines

1. Engines only (each engine, and the union).
2. `RAW`: same pipeline, no privacy layer, on OSS benchmark code only. Comparable to [ZeroFalse](https://arxiv.org/abs/2510.02534), [IRIS](https://arxiv.org/abs/2405.17238), [Vulnhalla](https://github.com/cyberark/Vulnhalla), [claude-code-security-review](https://github.com/anthropics/claude-code-security-review) and [Vulnhuntr](https://github.com/protectai/vulnhuntr) as external comparators.
3. Whole-function or whole-file at L2 (pseudonymised, not sliced) vs L3 (sliced), to separate the two effects.
4. Agent with full repository access as the context upper bound ([Sifting the Noise](https://arxiv.org/abs/2601.22952) setup).
5. Local fine-tuned small model with nothing leaving (LineVul-style classifier, [VulnLLM-R](https://arxiv.org/abs/2512.07533)) and L0/L1 with an open-weight model ([gpt-oss](https://arxiv.org/abs/2508.10925), Qwen coder): the "just self-host" alternative that competitors sell.
6. Privacy baselines: L1-only redaction (the CodeGate / Semgrep Multimodal posture); generic obfuscator renaming; [CodeCipher](https://arxiv.org/abs/2410.05797) on open-weight models where embeddings are accessible.
7. CodeQL on OSS benchmarks under its academic clause.

### 9.4 Experimental design and controls

- **Factorial ablation** in the style of [LLM4Vuln](https://arxiv.org/abs/2401.16185): privacy level x slice policy (thin / full / function) x pseudonym policy (kind-only / analysis-role; per-scan / per-request salt) x knowledge injection (none / CWE checklist / Vul-RAG) x model x prompt style (focused vs checklist; with vs without SAST label for the anchoring test; `analysis`-first vs strict JSON).
- **Contamination controls:** strip benchmark tell-tales at all levels; prefer post-cut-off CVEs; report synthetic and real-world numbers separately; note that renaming itself reduces memorisation effects.
- **Data hygiene:** de-duplicate, split by project and by time, manually validate a label sample, report label accuracy ([Croft et al.](https://arxiv.org/abs/2301.05456)); keep ground-truth-derived signals out of prompts.
- **Provider matrix:** at least two hosted frontier models, one reasoning model, and two open-weight models through vLLM or Ollama; snapshot model identifiers and deprecation dates in the artefact because providers retire snapshots.
- **Adaptive adversaries** for both leakage and injection experiments; static attack suites overstate robustness.
- **Harness:** [Inspect](https://inspect.aisi.org.uk/) (MIT): one Task per benchmark x level x model, a detection scorer and a second attacker Task for leakage; reproducible logs suit artefact evaluation. `mock` and `replay` providers keep CI free and deterministic.
- **Ethics and legality:** no client code in any experiment; `RAW` only on OSS; SecretBench under its data-protection agreement; CodeQL only under its academic clause.

### 10.2 The claim (hypothesis until E36 and E37 deliver)

> CodeKavach is, to our knowledge from this survey, the first open-source secure-code-review system that (1) sends hosted LLMs only an **analysis-derived minimal slice** in **reversibly pseudonymised** form through a **single audited, fail-closed egress**, and (2) reports, per privacy level and per model, **both** vulnerability-detection utility on real-CVE benchmarks **and** leakage measured by explicit identifier-recovery, reconstruction, domain-inference and re-identification attackers.

Supporting contributions that are individually modest but new in combination:

- A **four-step privacy ladder described in standard vocabulary** (ISO/IEC 20889 terms; EDPB pseudonymisation-domain model; ENISA pseudonym-policy axis) applied to source code.
- A **leakage metric suite for code sent to LLMs** (section 4.3), including disclosure-volume accounting that turns LLMxCPG-style reduction figures into a privacy measure, and metered `needs_context` expansion as a first-class privacy event.
- Evidence on the **dual role of comment and string neutralisation**: privacy control and prompt-injection defence (ALIBI-style attack success at L1 vs L2/L3).
- The observation that **pseudonymisation removes benchmark label leakage** (Juliet, OWASP Benchmark), which makes L2 numbers a cleaner estimate of real capability.
- A **per-CWE map of where privacy is cheap and where it is expensive**, with authorisation and business logic as the hard case.
- A small **Indian-regulator overlay** (RBI, SEBI, CERT-In, DPDP) on top of OpenCRE, which no public mapping provides, and a CERT-In report profile.
- An **MIT rule pack and engine matrix that is legally usable on proprietary bank code**, which CodeQL-based academic systems (IRIS, Vulnhalla, ZeroFalse's setup) are not.

### 10.3 What we must not claim

- That pseudonymised code "cannot be understood" by the provider. It can; the claim is measured reduction, per attacker, per level.
- That a filter or prompt wording prevents prompt injection.
- That results on Juliet or OWASP Benchmark predict real-world recall.
- "Big-Four-grade" as a quality claim. The defensible statement is that the report *structure and field set* are derived from a documented corpus of public professional audit reports and regulator requirements.
- Novelty beyond the survey date. Re-run the competitor and arXiv scan before submission; this area moved monthly during 2026.

## 11. Open questions

1. **Pseudonym information content.** Kind-only (`var_3`) vs analysis-derived role labels (`tainted_param_1`): how much utility is gained and how much does the attacker gain? Is there a useful middle ground for authorisation logic (section 3.4)?
2. **Pseudonym scope.** Per-scan determinism enables caching and multi-slice reasoning; per-request randomisation reduces linkability. Which default, and can the aggregation budget make per-scan safe enough?
3. **Public allowlist boundary.** Which third-party API names count as "well known"? Internal SDKs published on a public registry? Framework-mandated names that embed business terms (ORM model classes, route paths, message-queue topics, SQL table and column names inside strings)?
4. **Slice floor.** How small can a slice get before triage accuracy collapses, per CWE? Does delta-debugging minimisation with a local oracle pay for its cost?
5. **L4 expressiveness.** Which triage questions can be answered from relational facts alone (NESA / LLM4PFA style), and what is the fact schema? Does a fact stream leak structure comparable to a thin slice?
6. **Hotspot discovery under a disclosure budget.** How are unflagged security-relevant slices selected and ranked so that the `discover` task adds recall without sending most of the repository?
7. **Attacker strength.** Is a prompted frontier LLM a stronger identifier-recovery and domain-inference attacker than a fine-tuned DOBF-style model? How do we keep the attacker adaptive without overfitting the defence to it?
8. **Ground truth for business-logic leakage.** Who writes the reference "business logic summary" per benchmark application, and how is attacker output scored reproducibly (rubric, LLM judge with human validation)?
9. **Does pseudonymisation change gullibility?** RealVuln-style false-positive traps and ALIBI-style comments at each level: does removing natural language make the model more or less easy to fool through *code-level* decoys?
10. **Severity under pseudonymisation.** Does CVSS vector estimation degrade when the model cannot see what the data is? How much can be derived deterministically instead?
11. **Stylometry.** Is AST-normalising pretty-printing worth a possible utility cost, and does it matter when the client is already known to the provider through the account?
12. **Client identity and account model.** Whose API key is used in an audit engagement, and what does that imply for G4 and for RBI outsourcing classification?
13. **Regulatory classification.** Is an L3 payload "source code" or personal data for the purposes of the RBI outsourcing direction, DPDP and the EDPB guidelines (the latter were verified only in their public-consultation version)? Needs legal input, not engineering.
14. **Ingest hardening sources.** The completeness pass added four sources on archive bombs, Zip Slip, hostile git repositories and ReDoS (section 7, RESOURCE.md section 1.9). Still missing: published evidence on parser-level resource exhaustion in tree-sitter grammars and on hostile Git LFS or sparse-checkout behaviour. Close that with a short targeted search or our own fuzzing notes before E06 and E40 are closed.
15. **Reproducibility.** How to make LLM-dependent results reproducible enough for artefact evaluation given non-deterministic inference and model deprecation: cassette replay, open-weight reruns, or both?
16. **Sustainability.** CodeGate and LLM Guard were archived within about two years. What keeps the rule pack, engine adapters and provider-capability table maintained after the university project ends?

## Appendix A. Source caveats that affect citations

- **OWASP URL migration.** `owasp.org/www-project-*` now redirects to `owasp.org/projects/*`; the classic ASVS page and the classic Code Review Guide PDF path returned 404 during the survey. Use [ASVS v5.0.0 on GitHub](https://github.com/OWASP/ASVS/tree/v5.0.0) and [the Code Review Guide project page](https://owasp.org/projects/code-review-guide). Re-check every OWASP link before submission.
- **OWASP Top 10:2025 status.** The live page does not say RC or final; MITRE's CWE-1450 view is still titled RC1 in CWE 4.20. State which was used. The repository licence (CC BY-SA 4.0) and the site footer (CC BY 3.0) disagree.
- **SEI CERT Coding Standards** moved from the Confluence wiki to `cmu-sei.github.io/secure-coding-standards/`; old wiki citations will rot.
- **Clause-level detail not independently re-read:** RBI 2016 Cyber Security Framework Annex 1 wording; RBI IT Governance MD paragraph numbering; RBI DPSC clause numbers; SEBI CSCRF secure-SDLC and SBOM provisions; DORA Art. 25 wording; CRA dates; individual category names of the OWASP Agentic Top 10. Confirm against primary PDFs before quoting.
- **Bot-protected sites** (iso.org, misra.org.uk, PCI document PDFs) were confirmed only through search listings. Cite landing pages.
- **NIST AI DOIs** for AI 100-1 and AI 600-1 returned 404 through doi.org; cite the nvlpubs PDFs or CSRC landing pages. `first.org/epss/model` and `/epss/api` are 404; use [first.org/epss/](https://www.first.org/epss/).

- **Preprints.** A large share of the 2025 and 2026 evidence in sections 1 to 4 is arXiv-only. Grades [A] mark these; prefer [P] sources for load-bearing sentences in the paper and re-check venues before submission.
- **Living documents** (CWE, Cheat Sheets, CERT, OpenSSF guides) carry the access year, not a publication year.
